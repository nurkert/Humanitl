# ADR-0018 · Parity: every capability is an RPC first, UI and CLI are thin clients

Applies to: Humanitl 0.1

Status: Accepted
Date: 2026-09-02

## Context

Humanitl has two user interfaces: a graphical one and one on the command line
(ADR-0013). Both are gRPC clients of the same daemon (ADR-0003). This
arrangement predictably falls apart if it is not actively maintained.

The usual course: a function is needed in the UI and built there because it is
quicker — a filter, a sort order, a preview, a small conversion. Six months
later the UI contains domain logic, the CLI cannot do half of it, and an
attempt at automation fails because of a function that exists only with a
mouse. From then on the UI is the gatekeeper that principle 10 rules out.

The second course is silent divergence: the same capability exists in both
interfaces, but with different names, different defaults and slightly
different behaviour. Neither can be prevented by discipline alone.

## Decision

**There is exactly one interface to the core: the gRPC proto `humanitl.v1`.**
Every capability — deciding, rules, sandbox, terminal, doctor, discovery,
configuration, audit, export — is first designed as an RPC and implemented in
the daemon. UI and CLI call RPCs exclusively and contain **no domain logic**.

**Order and the obligation to ship along.** The implementation works
GUI-first, but: every issue that introduces a new RPC ships the CLI subcommand
in the same issue — even if it is only a `--json` output. Conversely, every
CLI subcommand gets a counterpart in the interface in the following sprint at
the latest.

**Parity table, generated and checked.** `docs/reference/parity.md` is
generated by `cargo xtask docs` from three sources: the service methods of the
proto, the clap structure of the CLI (subcommands with the attribute
`#[humanitl(rpc = "…")]`) and a UI registry (`app/lib/core/parity.dart`, list
RPC → screen). It has three columns: RPC, CLI subcommand, UI location. The CI
job `parity-check` **fails** if an RPC exists without a CLI row; missing UI
counterparts are listed as `warn`.

**Good defaults are part of parity.** The bundled profile `default` fully
describes the common use case: OpenCode, LLM in the LAN, ask mode `ask`, a
five-minute timeout, bundled block rules, session rules preferred. Whoever
changes nothing gets this route; whoever wants to change something finds every
value under the same key in the profile, in the settings screen and in the
CLI (ADR-0011).

## Rationale

The asymmetric strictness of the check is intentional. An RPC without a CLI
subcommand breaks the build; a missing UI counterpart is only a warning. The
reason: the expensive error is domain logic that is reachable only through
the interface — because it is then not scriptable, not testable without a
screen and not automatable. A missing UI counterpart, by contrast, is merely
an inconvenience that the next sprint fixes.

That the table is **generated** and not maintained is the difference between
a rule and a declaration of intent. A hand-maintained parity table would be
incomplete after the third sprint, and nobody would notice. Generating it from
proto, clap structure and UI registry pulls the truth out of the code; the
registry on the Dart side is the only hand-maintained part and small enough to
stay complete.

"Design as an RPC first" is moreover a design tool, not just an obligation.
Whoever phrases a capability as an RPC must name its inputs and outputs before
building a form. This encourages capabilities that are small and composable
instead of screens that do everything at once.

Including the defaults in parity closes a gap that is easily overlooked: two
interfaces can call the same RPCs and still start differently if each brings
its own presets. The bundled profile `default` is the one source for the
standard route; both interfaces load it, neither invents presets of its own.

## Rejected alternatives

- **Parity as a convention without a CI check.** Lasts until the first
  deadline. The same reasoning as in ADR-0015 for the dependency direction.
- **Generate the CLI from the proto.** Sounds consistent and results in an
  unusable command line: RPC boundaries are not subcommand boundaries, and a
  good CLI needs short forms, presets and task-oriented summaries. That is why
  the mapping is annotated (`#[humanitl(rpc = "…")]`) instead of generated.
- **CLI-first instead of GUI-first.** Would have secured parity just as well,
  but the product decisions are made at the screens. GUI-first with the
  obligation to ship along gets both.
- **Only the CLI, no UI.** Contradicts the target group: professionals without
  a security background who sit live next to the agent and are meant to make
  decisions in seconds.
- **Allow domain logic in the UI when it is small.** The beginning of every
  divergence. The boundary "small" cannot be defended, so it does not exist.
- **Parity table only as documentation without a CI job.** Would be wrong
  after three sprints and would then actively mislead.

## Consequences

- The effort per capability rises: RPC, daemon implementation and CLI
  subcommand in the same issue. The gain is an automatable application and a
  daemon that is fully testable without a screen.
- `cargo xtask docs` belongs to the toolchain and generates `parity.md`. The
  xtask crate is a helper tool outside the dependency rules and never contains
  runtime code (`backlog/CONVENTIONS.md` 3.1).
- The CLI attribute `#[humanitl(rpc = "…")]` on the clap subcommands is
  mandatory; without it the subcommand does not appear in the table.
- `app/lib/core/parity.dart` is a deliberately hand-maintained list RPC →
  screen. It is the only place where the mapping stands.
- Domain logic in `app/` or in `daemon/bin/humanitl` is an architecture
  violation, even when it is small (`docs/ARCHITECTURE.md` 3b).
- The fake daemon (HUM-005) implements the same proto and thus benefits
  automatically from every new capability — it is a third client of the same
  contract.
- This decision tightens ADR-0013: there the CLI is an equal client, here the
  equality is checked by machine.

## Affected issues

`HUM-078` (parity table and CI job `parity-check`), `HUM-003` (proto as the
only interface), `HUM-064` (CLI skeleton with RPC attributes),
`HUM-065` (`rules`/`flows` as the CLI counterpart), `HUM-070`
(`config`/`audit`/`daemon`), `HUM-066` (bundled profile `default`).
